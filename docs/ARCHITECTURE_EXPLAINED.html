Verity, for the owner. State of the code on 2026-10-22

How Verity fits together

A plain-language map of the whole system: what each part does, how one run moves through it, what the two halves must agree on, and where today's known problems live. Every file path below was checked against the code in backend/ and frontend/.

1. The big picture

In short: you describe a chip, a Python program (the orchestrator) asks Nemotron for Verilog, tests it in a locked-down Docker container against answers the AI cannot touch, fixes it, breeds better versions, proves the winner equal to the first working one, and streams every step to the website.

In one sentence: Verity is a website plus one Python server, where the server runs a fixed script that uses the AI only to write text (plans and Verilog) and uses real chip tools to judge that text.

  • Browser (frontend/): a Next.js app exported as plain static files. It holds no secrets. It only draws what the event stream says.
  • Backend API (backend/verity/api/): the front door. Checks tokens and rate limits, starts runs, streams events over SSE.
  • Orchestrator (backend/verity/orchestrator/): the run's script. Every decision (repair, keep, drop, stop) is an if in Python. The model is never asked what to do next (machine.py says so in its header).
  • Nebius models: Nemotron 3 Ultra writes plans, the first Verilog and repairs; Nemotron 3 Super writes the optimized variants (config.toml [routes.*]). Only backend/verity/llm/ talks to Nebius.
  • Docker sandbox: one image with the chip tools. Each check is a fresh container with no network. Only backend/verity/tools/ starts it.
  • Storage (backend/data/): verity.db (runs, candidates, events, daily spend) and a folder per run under data/runs/<id>/ with every attempt, log and the final runlog.json.
  • Recorded run (frontend/public/runs/): a saved event list in the same format as the live stream. golden.json is hand-made sample data; mac4-real.json is a real Nebius run from 2026-10-16.

The switch is one line: components/sections/studio/StudioView.tsx keeps a list REPLAY_RUNS = ["golden", "mac4-real"]. A ?run= value in that list replays a file; anything else is treated as a live run id. /results uses the same rule.

Live runs from the website always run in full mode. postRun in lib/sources/live.ts never sends mode, so the backend uses [limits] default_mode = "full". Fast mode is only reachable by calling the API directly.

3. Life of one run, step by step

In short: read the request, plan, give you 10 seconds to steer, rule-check the plan, lock the answer key, write and test v1 until it passes, measure it, breed and test better versions, pick the best by numbers, prove it equal to v1, compare with a human design, finish.

The real order is in backend/verity/orchestrator/machine.py, function _run. The grey word next to each title is the stage id the UI sees.

  1. Read the requestspec

    Loads the task pack, rendered at your knob values, and announces the run.

    Who: code only. UI gets: run running, human (your request), spec, a caption. File: orchestrator/plan_stage.py spec_stage

  2. Draft a planplan

    The model writes a short plan as JSON: blocks, widths, risks.

    Who: Planner role, Nemotron Ultra. UI gets: plan (revision 1), one op add_node per block, credits, artifact plan/plan.r1.json. File: plan_stage.py plan_stage, roles/planner.py

  3. Plan gate: 10 seconds to steerplan (gate)

    A countdown where you can pin a goal on a block, toggle a variant, hold, or build now. The first change triggers one replan by the model; later ones are applied in code.

    Who: you, then the Planner once more. UI gets: gate open / held / closed, human, plan revision 2 with a diff. File: plan_stage.py _gate_loop, _steer_block

  4. Feasibility checkplan

    Rules, not AI: at most 8 blocks (fewer if the pack says so), a line estimate under the pack's limit, the exact latency the pack needs, nothing like PLL, SRAM or multiple clocks. If it fails, the run ends before any Verilog is written.

    Who: code only. UI gets: stage plan done, or failed plus run error. File: orchestrator/feasibility.py check_plan

  5. Lock the answer keylock

    Re-checks the pack's hashes and publishes the golden model and testbench so you can read them. The agent can never change them.

    Who: code only. UI gets: golden node pending then locked, artifacts tests/golden_model.py and tests/test_dut.py. File: machine.py _lock_stage

  6. Write v1rtl

    Three drafts are written in parallel; each gets one quiet sandbox check and the one passing the most tests becomes v1's first attempt.

    Who: RTL generator role, Nemotron Ultra ([baseline] samples = 3). UI gets: candidate c1 drafting, credits. File: machine.py _baseline_stage, build.py sample_baseline, roles/rtl_gen.py

  7. Test v1lint, sim

    One sandbox call: port check (Yosys), lint (Verilator), then simulation (Icarus Verilog + cocotb) against the golden model.

    Who: Docker sandbox, sandbox/bin/verify. UI gets: stage lint / sim, candidate linting, simulating, then pass or fail with expected vs got. File: build.py evaluate, _check_attempt; tools/local_docker.py

  8. Repair v1 if it failsfix

    First a free code fixer for simple declaration errors, then up to 2 model repairs. The same failure twice means "start again from the plan". Still failing: the run ends with "no passing baseline".

    Who: core/rtl_fixer.py, then Repair role, Nemotron Ultra. UI gets: stage fix, candidate fixing, a "Diagnosis" caption. File: build.py _auto_fix, _repair, _restart; roles/repair.py

  9. Measure v1synth

    Turns v1 into gates (Yosys, Nangate45 library) for area, and times it (OpenSTA) for clock period. v1 becomes the yardstick: score 0.

    Who: sandbox/bin/measure. UI gets: candidate measured, artifacts reports/synth_v1.txt, reports/sta_v1.txt, circuit/c1.json. File: build.py measure, publish_reports

  10. Evolve better versionsevolve

    Full mode only. Round 1: three children of v1 (SIMPLIFY, OPTIMIZE, EXPLORE), built in parallel, each tested, allowed 1 repair, measured and scored. The best 2 are kept as elites. Round 2 (two more children) runs only if round 1 beat v1.

    Who: Optimizer role, Nemotron Super, then the sandbox. UI gets: stage evolve, round, candidate updates and captions (no per-step stage events). File: orchestrator/evolve.py evolve_stage, _round, _child

  11. Pick the winnerevolve

    Highest fitness wins (tie: smaller area). Numbers decide, never the model.

    Who: code. UI gets: winner (by ai), stage evolve done. File: evolve.py choose_and_prove, judge.py, core/fitness.py

  12. Prove it equals v1prove

    If the winner is not v1, Yosys EQY tries to prove both behave the same for every input. Not equal: dropped, next best tried (2 tries max, then v1). Undecided: shown as "Tested, not proven". Your winner override, if any, is applied right after.

    Who: sandbox/bin/eqy. UI gets: stage prove, candidate with eqy, a proof edge, reports/eqy_<label>_vs_v1.log. File: evolve.py _prove, apply_winner_override

  13. Compare with a human design(no stage)

    If the pack has a hand-written reference.v, it is measured with the same tools and checked with EQY against the winner. This never changes the run's result.

    Who: sandbox. UI gets: one human_ref event. File: orchestrator/human_ref.py

  14. Finish and savedone

    Final spend, a summary file, the end event, then the "Done" caption. The run manager writes runlog.json.

    Who: code. UI gets: credits, artifact reports/summary.json, run done (or cap_reached), caption "Done...". File: machine.py _finish, runs/manager.py

How a run can end early
  • error: a stage failed (plan rejected, no passing baseline, pack integrity), or a model or sandbox call broke. machine.py run_orchestrator catches it and calls _end_error.
  • cap_reached: a budget limit was hit. No new model calls; the best measured version still wins (_end_budget).
  • stopped: you pressed Stop. The run manager cancels the task and emits it (runs/manager.py).
  • error "timed out: no progress for 90 s": the watchdog (runs/watchdog.py, [watchdog] stall_s = 90).
  • error "server restarted": found still running at startup.

How POST /runs flows

  1. The bench sends {presetId, priority, params?}, with a Bearer token when auth is on. With [auth] required = false (today) your IP address is your session.
  2. api/routes.py create_run checks the token, the chip id and priority, and the "3 new runs per hour" limit.
  3. runs/manager.py create_run renders the pack at your knobs (core/family.py render_pack; a bad knob is a 422 with a readable sentence), then refuses with 429 if live is offline, the daily budget has no room, or a slot is taken.
  4. It writes the run row to SQLite (status queued, budget, pack hash, tool image digest, model ids), then starts the orchestrator and a heartbeat as background tasks.
  5. The answer is 201 {runId, capUsd, streamToken}. The bench puts the run id in ?run= so a reload rejoins.

How the event stream works

  1. The browser opens GET /runs/{id}/events?st=<streamToken>. The token sits in the URL because the browser's EventSource cannot send headers; api/redact.py hides it in logs.
  2. Every event the orchestrator emits goes through runs/hub.py (EventHub): stamp seq and tMs, save to SQLite first, then hand to each open stream.
  3. manager.py stream subscribes, sends saved events after Last-Event-ID, then follows live ones. No gap, no duplicate.
  4. api/sse.py writes id: <seq> plus data: <json>, sends : ping every 15 s, and keeps reading 5 s after the end event so the final "Done" caption arrives. A finished run with nothing new answers 204.

6. The contract between them

In short: 14 event types, each with seq, tMs and a type t. The live stream and every recorded file use the same events. If you change one side, change the other in the same commit.

Defined twice, kept in sync: backend/verity/contracts/events.py (Python, camelCase on the wire) and frontend/src/lib/contracts/types.ts plus schemas.ts (TypeScript and zod). Guards: backend/tests/contracts/, backend/tests/core/test_knob_parity.py, and npm run validate:fixture in frontend/.

7. Safety and money

In short: spending is checked before every model call, every run and every day; the AI only ever returns text, which runs in a sealed container; and production mode refuses to start unless auth and secrets are set. All keys below are in backend/config.toml.

Money: three layers

  • Per call (a reservation). Before each model call, llm/gateway.py asks runs/ledger.py reserve to hold the worst case: estimated prompt tokens plus that role's full output cap, priced from [prices]. If that could cross any run limit, the call never happens. Caps: [budget.call] plan_max_output = 12_000, rtl_max_output = 24_000, max_prompt_tokens = 12_000; [budget.parse] max_output_tokens = 600.
  • Per run. [budget.run]: max_usd = 0.50 (the one that usually binds), max_llm_calls = 20, max_input_tokens = 150_000, max_output_tokens = 200_000, max_candidates = 6, max_repairs_baseline = 2, max_repairs_child = 1, max_rounds = 2, max_wall_s = 900. Hitting one ends the run as cap_reached with the best measured version.
  • Per day. [limits] daily_usd = 5.00, stored in SQLite by UTC day. A new run is let in only if today's spend, plus the caps still held by runs in flight, plus this run's cap, fit under it. The fake provider counts as $0.

Sandbox isolation

  • Every tool call is a fresh container (tools/local_docker.py): --network none, read-only filesystem, --memory 2g, --cpus 2, --pids-limit 256, user 1000:1000, all Linux capabilities dropped, no-new-privileges, task pack mounted read-only, --pull never. Keys: [tools].
  • The model never gets a shell or tools. It returns text; code validates it (core/rtl.py rules, size cap [rtl] max_bytes) before any tool sees it.
  • The golden model, testbench and reference.v never go into a prompt. Pack files are hashed (MANIFEST.sha256) and re-checked before tool calls.
  • Time limits per tool: [timeouts] lint 20 s, sim 60 s, synth 120 s, sta 60 s, eqy 180 s.

Auth and access codes

  • [auth] required = false today: no login, your IP is your session. Production refuses this.
  • When on: POST /auth/session {accessCode} returns a session token valid 12 h (session_ttl_s). Codes are stored only as SHA-256 hashes (VERITY_ACCESS_CODE_HASHES). Each run gets its own stream token valid 30 min (stream_ttl_s). Tokens are signed with VERITY_SIGNING_SECRET (api/auth.py).
  • The Nebius key lives in backend/.env only. Nothing secret is in frontend/; NEXT_PUBLIC_* is for the public backend URL only.

Rate limits ([limits])

  • auth_per_ip = 10 per auth_window_s = 600; api_per_session_per_min = 60; runs_per_session_per_hour = 3; parse_per_session_per_min = 6.
  • concurrent_per_session = 1 and concurrent_global = 2 running at once.

Production guard

VERITY_ENV=production refuses to start unless: provider is nebius, the model host is api.tokenfactory.nebius.com, LLM_API_KEY is set, auth is required, the signing secret has 32+ characters, at least one access code hash exists, and CORS has no * (verity/config.py production_problems). The API docs pages are also turned off.

9. Glossary

In short: every term the code or the UI uses, one plain line each.

RTL, Verilog, SystemVerilog
Code that describes a chip. RTL is the level of detail (data moving between registers each clock tick); Verilog and SystemVerilog are the languages.
Task pack
One folder in backend/tasks/ per chip: the request text, port list, limits, golden model, testbench, optional human design, all hashed so nobody can edit them quietly.
Golden model
A simple trusted Python program (golden.py) that computes the right answers. The answer key.
Testbench
Test code (test_dut.py, cocotb) that feeds inputs to the design and compares outputs with the golden model.
Lock
The stage that re-checks the pack's hashes and shows the answer key, so you can see the agent cannot change it.
Preset, family, knobs, params
A preset is a chip the bench offers. A family is a preset with adjustable settings (knobs), like MAC lanes or bit width. params is the knob values sent with POST /runs; the server checks every range.
Parse
POST /parse: one English sentence goes to the model, which maps it to a family and knob values, or says it is out of range and suggests the closest. The server re-checks the answer.
Spec
The chip being built, as the UI sees it: ports, number of tests, line limit, goal.
Plan, plan gate
The model's block outline, then a 10 s countdown where you can steer before code is written.
Pin, toggle, steer
Pin a goal on a plan block, or switch a block's variant. Any such input is a "steer" (POST /runs/{id}/steer).
Feasibility gate
Code rules that reject an impossible or out-of-scope plan before any Verilog tokens are spent.
Candidate, version
One design idea. Code says candidate (c4); the UI says version (v4).
Attempt
One piece of Verilog inside a candidate. Attempt 1 is the original; later attempts are fixes.
Baseline, v1
The first version that passes all tests. Every number is shown relative to it.
Lint
An automatic check for code mistakes before running anything (Verilator).
Simulation
Running the design on a computer against the tests (Icarus Verilog + cocotb).
Synthesis
Turning Verilog into a list of real logic gates to measure its size (Yosys).
Nangate45
A free, open library of gates for a 45 nm process. Area numbers come from it.
OpenSTA, clock period
OpenSTA is the timing tool. Clock period is the shortest time per tick the design can handle; lower is faster.
PPA
Power, performance, area: the three things every chip trades off. Here: powerMw, clockPeriodNs, areaUm2, cellCount.
Fitness
One score per version: weighted percent gains vs v1. Area goal weighs area 0.60, timing 0.25, power 0.15; missing metrics are dropped and the rest re-weighted (core/fitness.py).
Operators: FIX, SIMPLIFY, OPTIMIZE, EXPLORE
How a version is made. FIX repairs a failing attempt in place. SIMPLIFY, OPTIMIZE and EXPLORE are the three strategies the Optimizer uses to create a new child. INIT marks v1.
Round
One batch of children: round 1 makes 3 from v1, round 2 makes 2 from the elites.
Elite
One of the best 2 measured versions so far. Round 2 builds on them.
REvolution-lite
Verity's small version of the REvolution paper's idea: a tiny population, keep the best, breed from them. Principles only, never its numbers.
EQY
Yosys's equivalence checker: a math proof that two designs give the same outputs for every input. Results: proven, not_equivalent, inconclusive ("Tested, not proven"), not_run.
human_ref, reference.v
A hand-written design in the pack. The human_ref event reports its PPA and EQY against the winner ("Verity vs human").
Fast and full mode
Fast stops after v1 is measured. Full adds evolve and prove. The website always uses full.
Orchestrator
The Python script that runs one run and makes every decision.
Role
One kind of model job: planner, rtl_gen, repair, optimizer.
Nemotron Ultra, Super; Token Factory
NVIDIA's models: Ultra is the big one (plans, first code, repairs), Super the cheaper one (optimized children). Token Factory is Nebius's service that hosts them.
Fake provider
VERITY_PROVIDER=fake: no model calls, $0. It returns canned plans and the pack's reference design so the whole pipeline can run for free.
Cassette
A saved model answer that is replayed instead of calling the model, for tests and evals (llm/cassette.py, backend/evals/cassettes/).
Sandbox, tool image
The Docker container with the chip tools (verity-tools:0.1), started fresh for every check with no network.
Declaration fixer
A free code-only fix for common declaration lint errors, tried before asking the model (core/rtl_fixer.py).
SSE
Server-sent events: one long HTTP response the server keeps writing events into.
Event, seq, tMs
One step of a run. seq is its number (1, 2, 3, no gaps); tMs is milliseconds since the run started.
RunLog
The full list of a run's events plus a header (format: "verity.runlog/1"). Recordings and GET /runs/{id}/log use it.
Golden run, recording, replay
A saved RunLog the site plays without the backend. golden.json is sample data; mac4-real.json is a real run.
Reducer
The single pure function (lib/run/reducer.ts) that turns the current state plus one event into the next state.
Caption, chapter
A one-line narration from a code template, grouped into chapters (Spec, Plan, Lock, Build and fix, Round 1, Round 2, Prove, Done).
Artifact
A small text file attached to the stream: plan, tests, synthesis and timing reports, EQY log, summary.
Credits, cap
Dollars spent so far, and the per-run limit.
Ledger, reservation
The per-run spending counter. A reservation is the worst-case hold it takes before each model call.
cap_reached
A run that stopped early because a budget limit was hit, keeping its best measured version.
Access code, session token, stream token
The code a judge types; the token it buys (12 h); and the per-run token used in the stream URL (30 min).
Watchdog, heartbeat
A timer that marks a run as failed if nothing happens for 90 s; the heartbeat is the "still alive" signal it watches.
Winner override
You choose a different measured version as the winner. Recorded as winner by user, with the AI's pick kept.
EventHub
The backend piece that numbers each event, saves it, then sends it to every open stream.

10. Docs vs code

In short: where a doc says one thing and the code does another. This page follows the code in every case.

  • Old folders on disk: the code lives in frontend/ and backend/. The old agent/ and web/ folders still exist locally (untracked) with a .venv, node_modules, env files and old run data. Nothing reads them; they can go once agent/data is moved or no longer needed.
  • backend/README.md: the endpoint table says GET /runs/{id}/log needs the owner's token, but api/routes.py run_log makes finished runs public; GET /runs exists but is not listed; setup says cd agent; "tests (written, not yet run)" is stale.
  • backend/ARCHITECTURE.md section 8 says there is no run listing endpoint (there is: GET /runs). Section 9.1 says canvas ops are sent by system; orchestrator/events.py sends add_node and connect as ai and only update_status as system.
  • backend/CONTRACTS.md section 9 says SSE closes after the terminal run event; api/sse.py keeps reading for up to 5 s (TERMINAL_GRACE_S) so the closing caption arrives, as backend/README.md notes.
  • frontend/ARCHITECTURE.md: its routes table has no /bench and calls /try a preset picker (it now forwards to /bench); it describes a React Flow canvas and a canvas store slice, but the store has run, playback, ui and live slices and the studio is a rack of modules; /studio defaults to mac4-real, not golden; section 1 still calls the backend "future".
  • HANDOFF.md says the backend tests all pass (386). The full suite on 2026-10-22: 409 passed, 1 failed (tests/tools/test_measure_power.py, because of the stale image, problem 1).
