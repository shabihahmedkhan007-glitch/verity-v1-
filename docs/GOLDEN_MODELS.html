Verity golden models

The locked answer key behind each chip, in plain language, so you can decide what to edit. Written 2026-10-22 from the files in backend/tasks and the code that uses them. Nothing on this page changes the product.

Four chips are live in the chat: add8, cnt8, mac4, fsm_seq. alu8, matmul4 and mm4_int4 are not. To leave feedback, type into the notes boxes and use the single copy button at the bottom.

In plain words

A golden model is the locked answer key for one chip. It is a short Python function: give it the inputs and it returns what the chip's outputs must be. Verity never asks the AI whether its own chip is right. It simulates the chip and compares every output with the golden model's answer.

Why it is locked. The AI that writes the Verilog is the party being graded. If it could change the answer key or the tests, a pass would mean nothing. So each chip has a task pack (golden model, tests, spec, ports, human reference, knob renderer) whose files are hashed into MANIFEST.sha256. The hash is checked when the backend loads the pack, again at the lock stage of every run, and again before every copy into a sandbox. A mismatch stops the run. The agent can only submit Verilog.

How a run uses it

  1. Lock. The run re-checks the pack hash, then publishes the golden model and the test file as artifacts so the UI can show them.
  2. Check a version. The tool image copies a fresh copy of the pack (golden.py, test_dut.py, task.toml, params.json) and the candidate Verilog (dut.v) into a sandbox (local Docker, or Nebius Sandboxes in production). Icarus Verilog simulates the Verilog and cocotb runs test_dut.py.
  3. Compare. For each step, test_dut.py drives the inputs, asks golden.py what the output should be, reads what the Verilog produced, and compares. Any difference, and any X or Z value, fails that case.
  4. Pass. A version passes only when the number of cases that ran equals test_count in task.toml, all of them passed, and no failure was recorded (sandbox/bin/verify). The winner is also checked against Verity's own v1 with EQY.
  5. Repair. If a version fails, the repair step gets the failing cases as data: inputs, the expected value and what the Verilog gave, at most 5 cases. It does not get the golden code.

  • In the Studio, the golden model item opens GoldenDetail (frontend/src/components/sections/studio/detail/ItemDetails.tsx): a "Locked" label, the test count, the list of tests/ file paths, and a "Show the golden model" button that reveals the Python source in a code view named tests/golden_model.py.   • params.json is not an artifact, so for a pack rendered at non-default knobs the code on screen reads PARAMS from a file the UI does not show.

The shared test harness (verity_tb.py)
  • Every test_dut.py imports backend/sandbox/lib/verity_tb.py, which lives in the Docker image at /verity/lib, not in a pack. It is not covered by any MANIFEST.sha256.
  • Edge convention: the clock starts low; inputs change and outputs are sampled only on the falling edge, so every rising edge sees stable inputs. A purely combinational design is driven, then sampled 1 ns later.
  • X and Z: read_int returns the unsigned value of a signal, or nothing if any bit is X or Z. Nothing never equals a golden value, so X and Z always fail.
  • Reset: reset_dut waits for a falling edge, drives reset active, holds it for 3 rising edges, and releases it on the next falling edge.
  • Cases: run_cases never stops at the first failure. A testbench exception counts as a failed case. Before any case runs it asserts that the number of cases equals test_count. It keeps at most 5 failures (with the stimulus text cut to 200 characters) and writes sim_result.json.
  • The file still carries a comment marking the cocotb version shims as UNVERIFIED. The first real run and the packs self-test have since passed (REPORT.md).

How the comparison works

  • Which clock edge: none. There is no clock. For each vector the test sets a, b and cin, waits 1 ns (settle(1)), then reads sum and cout.
  • What counts as equal: the pair (sum, cout) must equal the golden pair exactly. The first wrong vector ends that case; the failure text shows expected and actual sum and cout, and the inputs in hex. The other cases still run.
  • X or Z: if any bit of sum or cout is X or Z, read_int returns nothing, which never equals a number, so the case fails and the output is shown as X.
  • Latency and done: latency 0 and no done signal. The answer must already be correct 1 ns after the inputs change.
  • Start of the run: all inputs are set to 0 and given 1 ns before the first case. There is no reset.

How the comparison works

  • Which clock edge: the test changes rst_n and en on a falling edge, waits 1 ns, then waits for the next rising edge and the falling edge after it. It reads q at that second falling edge (half a clock after the rising edge) and compares it with the golden value.
  • Registered output check: before the rising edge, 1 ns after the inputs change, q must still equal the previous value. A design whose q moves before the edge (for example an asynchronous reset applied while q is not 0, or combinational logic) fails with "changed before the edge".
  • X or Z: a bit of q that is X or Z reads as no value and fails either check. Right after the initial reset q must read exactly 0, which is how a design with no working reset is caught (it leaves q at X in Icarus).
  • Latency and done: latency 1. The new q shows after the edge that sampled en. There is no done signal.
  • Reset: each case starts with rst_n low for 3 rising edges, released on a falling edge (reset_dut).

"""Golden model for mac4: LANES-lane unsigned LANE_BITS-bit multiply-accumulate over CYCLES accumulate edges.Pure function of its inputs: no I/O beyond reading params.json, no cocotb, no randomness. The testbench (test_dut.py)calls it and compares. The inputs on the start edge (edge 0) are not part of the sum. What each part does
  1. Lines 1 to 5 Docstring. Pure function; the testbench calls it; the knob values come from params.json.
  2. Lines 10 to 14 Reads params.json; LANES, LANE_BITS (the width knob) and CYCLES are the three knobs.
  3. Line 15 ACC_BITS = 2 x LANE_BITS + ceil(log2(LANES x CYCLES)), which is 22 at the defaults. The sum can never exceed it (I checked all 1,160 knob settings), so the width in task.toml comes from the same formula.
  4. Lines 16 to 17 ACC_MASK (all ones for the accumulator) and LANE_MASK (all ones for one lane).
  5. Lines 20 to 22 lane_products(a_lanes, b_lanes): for one accumulate edge, multiplies each lane's a by its b after keeping only LANE_BITS bits of each, so inputs are unsigned.
  6. Lines 25 to 34 golden_mac4(a_cycles, b_cycles) returns the final acc. a_cycles[k] and b_cycles[k] are the lane values present at accumulate edge k + 1. It adds up the lane products of every cycle and trims to ACC_BITS (which never changes the value). The inputs on the start edge (edge 0) are not in the lists, so they are not counted.

    What the packs self-test checks (from self_test.md)
    1. Integrity: the pack loads and MANIFEST.sha256 matches; make_manifest.py --check prints ok.
    2. Rules: reference.v passes the coding rules and size limits.
    3. Reference passes: the reference runs the locked tests in the real sandbox: status pass, total == passed == test_count, lint ok.
    4. Determinism: the same run twice gives the same cases.
    5. Measurable: the reference synthesizes with an area above 0.
    6. Mutants fail: every row in self_test.md for the pack must fail the locked tests (and still pass the coding rules, so the failure comes from the tests).
    7. Equivalence sanity (when EQY is enabled): reference against itself is never not_equivalent; reference against the first failing mutant is never proven.
    8. Pack unchanged: the pack hash after all runs equals the hash at the start.

  5. Be exact about what proves what. golden.py is Python and reference.v is Verilog. No tool compares them formally. They agree only because reference.v passes test_dut.py in the sandbox (self-test step 3), which is a simulation of the cases in the table above, not a proof.

    EQY (the formal tool) only ever compares two Verilog designs: in a run, the winner against Verity's own v1, and, for packs with a reference, the winner against reference.v (the human_ref step in backend/verity/orchestrator/human_ref.py). The self-test also uses EQY on the reference against itself and against one mutant, only as a sanity check of the proof path.

    So after an edit: make reference.v pass the new tests first (step above), then for the four families re-run the knob edges (test_family_edges.py), because each knob setting renders its own reference.v. A reference that no longer matches the new behavior shows up as a failing self-test, or later as a winner that EQY calls not_equivalent to it.
