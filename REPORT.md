### Backend at a glance

The backend (`backend/`, Python 3.13, FastAPI) is the agent: it takes a chip request, drives NVIDIA Nemotron on Nebius Token Factory through the whole design loop, runs every check in real open-source chip tools, and streams each step to the web app. Detail lives in `backend/ARCHITECTURE.md`; exact interfaces in `backend/CONTRACTS.md`.

| Part | What it does |
|---|---|
| The loop (`verity/orchestrator/`) | spec, plan, lock the golden model, write v1, lint, simulate, fix (repair the same version in place), synthesize, evolve (up to 2 rounds, at most 6 versions: v1 plus 3 plus 2, operators SIMPLIFY, OPTIMIZE and EXPLORE), pick the winner by measured fitness vs v1, prove it equal to v1 with EQY, then measure the human reference. Fast mode stops after v1; full mode is the default for judges. |
| Model roles (`verity/roles/`, `verity/llm/`, `config.toml` routes) | Planner, RTL writer and repairer run on Nemotron 3 Ultra; the optimizer runs on Nemotron 3 Super; the chat router on Nemotron 3.5 Lightning; the parser, chat answers and research summaries on GLM 5.3 (D16). GLM never writes Verilog. Every call goes through one gateway that records tokens, cost and finish reason against the run's budget. A fake provider gives $0 runs for tests and local checks. |
| Chip tools (`sandbox/`, Docker image `verity-tools:0.1`) | `verify`: lint (Verilator), interface check (Yosys), simulation (cocotb + Icarus). `measure`: Yosys synthesis on Nangate45, OpenSTA timing and a vectorless power estimate. `eqy`: Yosys EQY equivalence. `seeds`, `strength`, `wave`: the sign-off's extra seeds, planted bugs and waveforms. The AI never runs a tool directly; the backend calls fixed scripts with fixed arguments. |
| Task packs (`backend/tasks/`) | Each pack is a locked answer key: a human-written golden model (`golden.py`), a cocotb testbench, a human reference design (`reference.v`) and a SHA-256 manifest that is re-checked before every tool call. Seven packs; four of them (MAC array, adder, counter, sequence detector) are knob families that render a fresh locked pack for any in-range setting. The AI sees only the spec, the module header and the coding rules, never the tests or the reference. |
| Trust rules | Every PASS is a real simulation against the human-written golden model. "Proven" only when EQY proves it. Every number comes from a tool run and is stated against our own v1; the human-reference comparison is the one labelled exception (D14). |
| Fact check and research (`verity/core/parse.py`, `verity/research/`) | One GLM 5.3 call sorts a sentence into six classes and maps it onto a family and knob values; code sets the verdict and validates every answer against the knob tables (D17, D31). Hardware requests get up to three Tavily or Serper searches built from code templates, ranked by code and summarised by one GLM call with no tools (D19). The answer can only pre-fill the bench, never become a test or a reference. |
| API (`verity/api/`) | `GET /health` (live, budget, models, features), `POST /auth/session` (access code), `GET /runs` (public list), `POST /runs` (family, goal, knobs, research id), `GET /runs/{id}/events` (server-sent events, resumable), `GET /runs/{id}/log`, `POST /runs/{id}/steer`, `POST /runs/{id}/stop`, `POST /parse` (fact check), `POST /runs/{id}/ask` (chat after a run, D18). |
| Budgets and safety | Per-run cap $0.50 (enforced on the server), daily cap $5.00, 15-minute wall limit with a watchdog, one run at a time per session, rate limits on runs, parse and access-code attempts. API keys stay server-side in `backend/.env`. |
| Storage | SQLite for runs, events and daily spend (sessions are signed tokens, not stored), plus Verity's own knowledge store of research and run outcomes (migrations 3 and 4, D29), plus a folder per run with every prompt, answer, tool log and the final Verilog; a finished run is replayable as the same event stream the web app plays. |
| Quality | 681 automated tests passed on 2026-10-23 (orchestrator, API, contracts, research, ask, tools, packs, with Docker edge proofs at every knob family's limits); pack self-test with mutants; real-model gate (mac4 10 of 10, 2026-10-16) and range probe (17 runs, 2026-10-18). |

### 2026-10-01: Research paper review (REvolution)
- **Reviewed** `C:\Users\admin\Downloads\RTL generation with LLMs.pdf`: "REvolution: An Evolutionary Framework for RTL Generation driven by Large Language Models" (Min, Cho, Jang, Kang; POSTECH; ASP-DAC 2026; arXiv 2510.21407). The PDF is not stored in this folder.
- **Key points:**
  - Evolves a population of candidates, each a (Thought, Code, Feedback) tuple, instead of refining one design, to avoid getting stuck in a local optimum.
  - Dual population: Fail group gets bug-fix work, Success group gets PPA optimization; offspring split in proportion to group size.
  - Six prompt operators: Fix (Fail only), Fusion (Success only), Simplify, Explore, Refactor, Improve. Operator chosen by UCB bandit plus softmax, rewarded for producing a passing design or raising fitness.
  - Fitness = weighted relative gain vs a reference design in power, area and clock period; failing designs score minus infinity. Elites kept per PPA metric.
  - Setup: N=10, 10 offspring per generation, 20 generations (about 200 designs per problem); iverilog + Yosys with Nangate45; runtime 785 to 1990 s per problem.
  - Results: pass rate up to +24.0 points over the initial population; DeepSeek-V3 reaches 95.5% on VerilogEval. Beats 200 independent samples at the same call budget (ablation), so the loop matters, not just volume.
- **Caveats noted:** PPA gains are measured against non-optimized benchmark reference designs (authors say so); uniform 0.01 ns clock target; some designs passed simulation but failed after synthesis; relies on benchmark-provided testbenches and reference designs; budget limited by API cost.
- **Relevance to Verity:** direct evidence for the PPA-loop idea; supports keeping a post-synthesis equivalence check (Yosys EQY); operator and population view could become a dashboard panel. Recorded as an open decision (optimization loop design). Code at github.com/kmcho2019/REvolution; license not yet checked.
- **Verified by:** full text extracted with pypdf (7 pages) and read.
